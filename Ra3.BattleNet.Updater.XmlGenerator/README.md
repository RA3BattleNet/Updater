# Ra3.BattleNet.Updater.XmlGenerator

清单生成壳。业务逻辑在 `Ra3.BattleNet.Updater.Server.ManifestGenerator`（业务逻辑不住在可执行项目里），
本壳只负责"解析参数 → 调库 → 打印自检报告"。

## 用法

```
XmlGenerator --target-dir <本版目录> --new-xmloutputpath <清单输出路径> [选项]

  --old-xmlpath <路径>       上一版清单（用于继承 UUID；链式生成时必须提供）
  --old-root <目录>          上一版文件根目录（自检要算补丁率、自动关联要看尺寸时必需）
  --target-dir <目录>        必需，本版文件所在目录
  --new-xmloutputpath <路径> 必需，本版清单输出路径
  --exclude-dirs <列表>      逗号分隔的顶层目录名，其下文件标记为 Mode=Skip
  --report <路径>            把自检报告额外写一份到文件
  --no-auto-link-uuids       关掉自动关联 UUID（**默认是打开的**，见下）
  --auto-link-uuids[=name]   选择自动关联的形态：默认「同名优先 + 尺寸兜底」；
                             =name 只信「同名」这个强信号，更保守
  --help
```

发布流水线的推荐调用（**必须按版本顺序链式生成**，否则 UUID 链断裂 → 补丁全部落空且不报错）：

```powershell
XmlGenerator --old-xmlpath v4.xml --old-root <v4目录> `
             --target-dir    <v5目录>  --new-xmloutputpath v5.xml `
             --report reports/v5.report.txt `
             --auto-link-uuids
```

## 清单里 `File/UUID` 的四条来路

| # | 来路 | 覆盖的场景 |
|---|---|---|
| 1 | `(FileName, Path)` 完全相同 → 继承 | 内容变了、路径没变 |
| 2 | `MD5` 相同 → 继承 | **纯改名/纯移动**（内容没变） |
| 3 | 相对路径确定性派生（MD5 of lowercased path） | 真正的新文件（与内容无关，保证可复现） |
| 4 | **自动关联**（**默认开启**，`--no-auto-link-uuids` 可关） | **路径和内容同时变**（下面详述） |

第 4 条是唯一"猜"的一环，但**默认开启**（需求方 2026-09-27 决定）；其余三条都是确定的。

> **为什么敢默认开**：它只影响"客户端拿谁当前身"，而这一层有两道校验兜底 ——
> 客户端打完补丁要校验目标 MD5（对不上就回落完整下载）、服务端有"补丁不小于目标文件就弃用"。
> 配错的最坏结果只是白跑一次 hdiffz + 客户端一次回落，**不会写坏文件、不会让更新失败**。
> 关掉用 `--no-auto-link-uuids`；想更保守（只信同名、不做尺寸兜底）用 `--auto-link-uuids=name`。

## 为什么需要第 4 条：路径 + 内容同时变，确定性规则认不出来

规则 1、2 都要求"有一头没变"。可真实发布里有一类版本是**两头都变**的：把一整套运行时
从一个目录搬到另一个目录，同时升级大版本。最典型的实测例子（v4→v5）：

```
v4:  bin\System.Private.CoreLib.dll                                  11.96 MB
v5:  dotnet\shared\Microsoft.NETCore.App\10.0.5\System.Private.CoreLib.dll   14.82 MB
```

路径变了、内容也变了 ⇒ 规则 1 不匹配、规则 2 不匹配 ⇒ 生成器把它记成"消失 1 个 + 新增 1 个"。
后果不是报错，而是**静默退化**：客户端找不到前身 ⇒ 只能完整下载。

实测 v4→v5 这一对版本（3789→3935 个文件）：

| | 补丁命中 | 命中率 | 客户端要下 |
|---|---|---|---|
| 不开自动关联 | 30 | **4.7%** | 274,122,491 字节 |
| 开自动关联（463 对） | 492 | **76.5%** | **151,610,219 字节** |

614 个新增 / 463 个消失里，**458 对靠"文件名相同"就配上了** —— 换句话说，**信号一直在数据里，
只是没人用它**。而"整块替换运行时"这类发布恰恰是最需要省字节的那种（不省的话，
274 MB 比整包 166.8 MB 还贵）。

## 猜测的逻辑：先强信号、后弱信号、贪心 1:1（默认启用）

```
第一轮（强信号）：同名优先
    按 FileName（大小写不敏感）给"消失集合"建索引；
    对每个"新增"文件，取同名候选里**尺寸最接近**的那个（score = min/max，越接近 1 越像）。
    配上的对从池子里拿走（一个消失文件只能被认领一次）。

第二轮（弱信号）：尺寸窗口兜底   ← 只有 --auto-link-uuids 不带 =name 时才做
    第一轮没配上的新增文件，在剩余消失文件里找尺寸相差 ≤2 倍的，同样取最接近的。
    这一轮是为了覆盖"连文件名也改了"的改名（实测只多配到 5 对）。
```

为什么这么排：

- **文件名是最强、最便宜的证据。** 搬家/重打包这类发布里文件名几乎不变；同名不同内容
  正是"同一个东西被重做了"。而且它不需要任何 IO 或进程调用，是一次字典查找。
- **尺寸只是弱证据，所以放第二轮、还加窗口。** 大量文件的尺寸本来就落在同一量级
  （几百个 `*.resources.dll`），只按尺寸配对会造出大量假对。2 倍窗口 + 取最接近 +
  1:1 认领，把假对的量压到可接受。
- **贪心 1:1 是硬约束。** UUID 在清单里必须唯一：新清单读取时会**跳过重复 UUID 的条目**，
  所以同一个消失文件绝不能被两个新增文件认领。

## 配错了会不会坏？不会

关联只影响一件事：**客户端拿谁当"前身"去试补丁**。两道校验兜住：

1. 客户端打完补丁会**校验目标文件的 MD5**，对不上立即回落完整下载；
2. 服务端生成补丁时有"**补丁不小于目标文件就弃用**"的规则（§5.3），无用的补丁不会进库。

所以最坏的结果是：白跑一次 hdiffz + 客户端多一次往返（探测补丁 404 或校验失败），
**不会写坏文件，也不会让更新失败**。这也是为什么敢默认把它做成"一个开关"而不是
"必须人工逐条确认"——它**默认开启**（`--no-auto-link-uuids` 可关），因为它是全流程里唯一带猜测的一步，
所以必须留一个一键退路；真正的兜底是下面那两道校验，不是"默认关"。

## 报告里能看到什么

开启后，报告会**最先**列出已经改过清单的动作，并给出每一对的依据：

```
  ✔ 已自动关联改名 463 对（同名 458 对 / 尺寸接近 5 对）：
    依据：文件名相同优先；同名有多个候选时取尺寸最接近的；
          同名配不上的再看尺寸是否在 2 倍以内；一对一只用一次。
    这些新增条目的 <UUID> 已被改成前身的 UUID —— 客户端因此可以打补丁。
    → /dotnet/shared/Microsoft.NETCore.App/10.0.5/System.Private.CoreLib.dll
      前身 /bin/System.Private.CoreLib.dll   (依据 同名，大小接近度 81%)
    …另有 443 对未列出（报告只列前 20 对）
```

关掉自动关联时，报告给出的是**候选建议**（`➜ 操作: 把新增条目的 <UUID> 改成 …`），
供人工逐条确认后手改 XML。

【必须】自动关联打开时，**已关联的那几对不会再出现在"需要人工确认"列表里** ——
否则会让人去改一个已经改好的 UUID（这条有测试钉着）。列表里剩下的是
"同名和尺寸都没线索、只能靠 hdiffz 探测给建议"的那些。

## 已知边界

- **文件名和尺寸都没留下线索**（改名 + 大改内容 + 变更量还很大）时配不出来 —— 这种只能人工。
  自检报告的"疑似前身"探测（`消失 × 新增` 跑 hdiffz，有界的 200 对）就是给这种情况兜底的。
- 尺寸窗口用的是"新增文件 vs 消失文件"的**磁盘尺寸**，两边都必须能读到；`--old-root`
  缺失时自动关联**不做任何事**（不会瞎猜）。
- 自动关联**只处理"消失 × 新增"**。已经按规则 1/2 继承过的条目不会重复参与。
